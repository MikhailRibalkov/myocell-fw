# myocell: руководство

Система записи поверхностной ЭМГ: плата **myocell_s3** (ESP32-S3 + ADS1298) снимает сигнал и передаёт его по Wi-Fi, программа **receiver** на компьютере находит плату, показывает сигнал в браузере и записывает его в файлы.

```
 электроды ─► ADS1298 ─SPI─► ESP32-S3 ──── Wi-Fi, TCP 5005 ────► receiver ─► браузер
                              │  12 МиБ буфер в PSRAM               │   http://127.0.0.1:8080
                              └── UDP 5006: ответ на поиск ◄────────┘   recordings/*.csv
```

## 1. Состав репозитория

Пять независимых крейтов, у каждого свой `Cargo.lock`. Общего workspace нет: прошивка собирается под Xtensa своим тулчейном, остальное — обычным stable Rust.

| Крейт | Где работает | Назначение |
|---|---|---|
| `firmware` | ESP32-S3, `no_std` | Захват с ADS1298, буфер, Wi-Fi, TCP-сервер, ответы на поиск |
| `ads1298` | везде | Драйвер АЦП: регистры, команды, разбор кадров. Async, плюс блокирующее чтение кадра |
| `protocol` | везде | Формат пакетов данных, подтверждений и поиска; настройки каналов (`setup.rs`) |
| `backlog` | везде | Кольцевой буфер «записано / отправлено / подтверждено» без блокировок |
| `receiver` | компьютер | Поиск плат, приём, статистика, веб-интерфейс, запись в CSV |

`ads1298`, `protocol` и `backlog` не зависят от железа и тестируются на компьютере обычным `cargo test`.

## 2. Плата

**myocell_s3, ревизия 2026.r1.** Схема и разводка: KiCad-проект <https://github.com/RF-Lab/emg-lab/tree/main/myocell_s3>.

- Модуль ESP32-S3-WROOM-2: восьмилинейная (octal) флеш-память 32 МБ и PSRAM.
- АЦП TI ADS1298, 8 каналов по 24 бита, работает от внутреннего генератора 2,048 МГц.
- USB-C: питание и встроенный в ESP32-S3 USB-Serial-JTAG (прошивка и лог без отдельного преобразователя).

### Подключение ADS1298 (`firmware/src/board.rs`)

| Сигнал ADS | GPIO | Примечание |
|---|---|---|
| SCLK / DIN / DOUT / CS | 12 / 11 / 13 / 10 | GP-SPI2, режим 1, 8 МГц |
| /DRDY | 14 | Также заведён на PCNT (счёт преобразований) и захват MCPWM (метки времени) |
| START | 21 | |
| /RESET | 48 | Домен 1,8 В: сброс делается командой SPI, вывод держится в «1» |
| /PWDN | 8 | |
| CLK | 47 | Только вход: АЦП работает от своего генератора. Нельзя включать `CLK_EN` |

Кнопка BOOT (GPIO0) и делитель батареи (GPIO7, ADC1 канал 6) выведены в `Board`, но пока не используются.

### Электроды

Площадки на нижней стороне платы, по два столбика:

```
 (верх платы, у разъёма USB)
   J6  IN4−          J3  IN3−
   J4  IN4+          J2  IN3+
            J8  RLD
```

Используются CH3 (правый столбик) и CH4 (левый). CH1/CH2 выведены на шлейфовый разъём J1, CH5–CH8 не используются. Электрод **RLD** (J8) задаёт потенциал тела и подавляет синфазную наводку: им нужно касаться тела, иначе наводка 50 Гц на порядки сильнее.

### ⚠ Известная проблема сборки

На имеющемся экземпляре платы **не запаяны резисторы смещения входов**: R3, R4, R5, R10 (CH3) и R22, R23, R24, R33 (CH4), хотя по схеме они должны стоять. Входы развязаны конденсаторами 2,2 мкФ, и без резисторов узел на стороне АЦП «висит»:

- смещения в сотни мВ со скачками и медленным возвратом при плохом контакте;
- ЭМГ в десятки раз слабее нормы;
- лишний шум (у CH4 около 16 мкВ против 0,6 мкВ собственного шума АЦП).

Сам АЦП исправен: с входами, замкнутыми внутри микросхемы, оба канала дают около 0,57 мкВ RMS в полосе 20–450 Гц. Решение аппаратное. По схеме стоят 10 кОм, но это даёт входное сопротивление около 20 кОм и ослабляет сигнал. Разумный компромисс — **около 1 МОм** (срез ФВЧ около 0,15 Гц, установление около 1 с). Номинал согласуйте с разработчиком платы.

## 3. Прошивка: как устроена

### Задачи и приоритеты

| Задача | Где выполняется | Что делает |
|---|---|---|
| `acquisition_task` | `InterruptExecutor`, приоритет 2 | Ждёт /DRDY, читает кадр **блокирующим** SPI, кладёт в буфер |
| обработчик GPIO | прерывание, приоритет 3, в IRAM | Ставит метку времени входа в прерывание, будит задачу захвата |
| `stream_task` | основной executor | TCP-сервер на порту 5005: отправка пакетов и приём подтверждений |
| `discovery_task` | основной executor | Отвечает на поиск по UDP 5006 |
| `connection_task`, `net_task`, `link_monitor_task` | основной executor | Wi-Fi, стек TCP/IP, переподключение при «залипании» канала |
| `report_status` | основной executor | Раз в секунду пишет в лог состояние |

Задача захвата вытесняет всё остальное, а её прерывание стоит выше прерываний Wi-Fi (у них уровень 1): каждый кадр нужно прочитать раньше следующего /DRDY, это 500 мкс при 2000 отсчётах в секунду.

### Данные без потерь (store-and-forward)

1. Каждый кадр получает **номер преобразования** от аппаратного счётчика PCNT. Разрыв в номерах означает реальную потерю, а не догадку по времени.
2. Кадры копятся в кольцевом буфере **12 МиБ в PSRAM**, это около 3 минут при 2 kSPS.
3. Компьютер подтверждает принятое (ACK раз в 100 мс). Из буфера уходит только подтверждённое.
4. После обрыва связи плата досылает всё неподтверждённое, а приёмник отбрасывает повторы по номеру кадра.

Пока к плате никто не подключён, буфер заполняется. Через ~3 минуты новые кадры начнут теряться (счётчик `overruns` в логе).

### Сеть

- Плата подключается к Wi-Fi с SSID и паролем, **зашитыми при сборке** (см. раздел 5).
- **TCP 5005**: плата слушает и принимает **одного** клиента. Пока он подключён, другой подключиться не может.
- **UDP 5006**: плата отвечает на запрос поиска своим MAC, портом данных, версией прошивки и адресом текущего клиента.

Форматы описаны в `protocol/src/lib.rs` (данные и ACK) и `protocol/src/discovery.rs` (поиск).

### Лог платы

Раз в секунду печатаются две строки, например:

```
tx 50 pkt/s, send max 0.2 ms, backlog 168 (0.0 s) | tcp up, losses 0 | rssi -57 dBm, disconnects 0, stall reconnects 0
ads: max us (worst): edge->isr 72 (131), isr->task 91 (116), edge->read done 245 (313) | missed 0, overtaken 0, overruns 0, read errors 0
```

| Поле | Значение |
|---|---|
| `tx … pkt/s` | Отправлено пакетов (по 40 кадров) за секунду, в норме 50 |
| `backlog N (T s)` | Не подтверждено записей (и сколько это секунд) |
| `losses`, `disconnects`, `stall reconnects` | Обрывы TCP, обрывы Wi-Fi, принудительные переподключения медленного канала |
| `edge->isr` | От спада /DRDY до входа в прерывание. Это время, когда прерывания запрещал драйвер Wi-Fi |
| `isr->task` | От прерывания до задачи захвата |
| `edge->read done` | От /DRDY до конца чтения кадра. Должно быть меньше 500 мкс |
| `missed` | Реальные потери преобразований по счётчику PCNT |
| `overtaken` | Следующий /DRDY пришёл во время чтения, кадр мог испортиться |
| `overruns` | Буфер был полон, кадр отброшен |

Без Wi-Fi путь до прочитанного кадра занимает около 50 мкс; с Wi-Fi худший случай около 300 мкс. Запаса хватает для 2 kSPS, но не для 4 kSPS.

## 4. Инструменты для прошивки

У ESP32-S3 ядро **Xtensa**, которого нет в официальном Rust, поэтому нужен форк компилятора от Espressif (тулчейн `esp`). Его ставит `espup`.

### macOS и Linux

```sh
cargo install espup espflash cargo-espflash --locked
espup install                      # тулчейн esp + линкер xtensa-esp-elf
. ~/export-esp.sh                  # PATH к линкеру и LIBCLANG_PATH
```

Строку `. ~/export-esp.sh` стоит добавить в `~/.zshrc` или `~/.bashrc`, иначе её нужно выполнять в каждом новом терминале. `espup` обновляет этот файл сам при `espup install` и `espup update`.

Версии, на которых проверено: тулчейн `esp` 1.97, `espflash` 4.7, `espup` 0.19. В `firmware/Cargo.toml` указано `rust-version = 1.95`, а `espflash` 4.7 при установке требует stable Rust 1.95 или новее (`rustup update stable`).

**Linux, доступ к порту.** Плата видна как `/dev/ttyACM0`. Пользователь должен входить в группу `dialout` (Debian/Ubuntu) или `uucp` (Arch):

```sh
sudo usermod -aG dialout $USER     # затем выйти из сеанса и войти снова
```

### Windows

```powershell
cargo install espup espflash cargo-espflash --locked
espup install
. $HOME\export-esp.ps1
```

Драйвер для встроенного USB-Serial-JTAG Windows 10/11 ставит сам. Плата появится как `COMx`.

### Проверка

С подключённой платой:

```sh
espflash board-info
```

Должны появиться `Chip type: esp32s3`, флеш 32 МБ и MAC-адрес.

## 5. Настройка сети и прошивка платы

Данные Wi-Fi вшиваются в прошивку **при сборке** макросом `env!`. После смены сети плату нужно пересобрать и прошить заново.

### 5.1. Файл с настройками сети

```sh
cd firmware
cp .cargo/secrets.toml.example .cargo/secrets.toml     # если файла ещё нет
```

`firmware/.cargo/secrets.toml`:

```toml
[env]
WIFI_SSID = "имя-сети"
WIFI_PASSWORD = "пароль"
```

- Файл в `.gitignore`, в репозиторий он не попадёт.
- Нужна сеть **2,4 ГГц** с WPA2-Personal: ESP32-S3 не поддерживает 5 ГГц.
- Адрес компьютера в прошивке не нужен: приёмник находит плату сам. Строка `HOST_ADDR` из старых версий ни на что не влияет, её можно удалить.

### 5.2. Сборка и прошивка

```sh
cd firmware
. ~/export-esp.sh            # если не добавлено в профиль оболочки
cargo run --release
```

`cargo run` собирает прошивку и через `espflash` (настроен как runner в `.cargo/config.toml`) прошивает плату и открывает её лог. Выход из лога: `Ctrl+C`.

Меняется только `secrets.toml`, но Cargo сам заметит изменение переменных окружения и пересоберёт прошивку.

Отдельные шаги, если лог не нужен:

```sh
cargo build --release
espflash flash --chip esp32s3 target/xtensa-esp32s3-none-elf/release/myocell-fw
espflash monitor --chip esp32s3      # лог, когда понадобится
```

После прошивки в логе должно появиться:

```
Wi-Fi connected to "имя-сети"
IP address: 192.168.1.61/24
Discovery: answering on UDP port 5006
```

Если сеть не найдена или пароль неверен, плата пишет `Wi-Fi connect failed` и повторяет попытки каждые 2 с.

### 5.3. Прошивка на другом компьютере без исходников

Для прошивки нужен только `espflash` и файл прошивки (ELF). Тулчейн `esp` не нужен.

1. На компьютере со сборочным окружением соберите прошивку **с нужными данными сети** и скопируйте файл `firmware/target/xtensa-esp32s3-none-elf/release/myocell-fw`.
2. На другом компьютере установите `espflash`: `cargo install espflash --locked` или готовый исполняемый файл со страницы релизов <https://github.com/esp-rs/espflash/releases>.
3. Прошейте:

   ```sh
   espflash flash --chip esp32s3 myocell-fw
   ```

Учтите, что в файле прошивки **открытым текстом лежит пароль Wi-Fi**. Передавайте его как секрет.

## 6. Настройка АЦП

Все настройки каналов в одном месте: `protocol/src/setup.rs`. Этот файл используют и прошивка (чтобы настроить АЦП), и приёмник (чтобы пересчитать отсчёты в микровольты), поэтому они не могут разойтись.

| Константа | Сейчас | Что задаёт |
|---|---|---|
| `DATA_RATE` | `Sps2k` | Частота отсчётов, 2000 в секунду |
| `CHANNEL_CONFIG` | CH3, CH4: усиление 12; остальные выключены | Усиление и режим входа каждого канала |
| `RLD_SENSE` | CH3, CH4 | Каналы, по которым строится сигнал RLD |
| `CONFIG3` | внутренний опорный источник, буфер RLD | Опора и RLD |

После изменения `setup.rs` нужно **прошить плату и пересобрать приёмник**. Тест `rld_senses_only_enabled_channels` проверяет, что RLD строится только по включённым каналам.

Шкала входа равна ±2,4 В / усиление, то есть ±200 мВ при усилении 12. Приёмник показывает, какую долю шкалы занимает сигнал, и предупреждает о насыщении.

## 7. Приёмник (receiver)

### Запуск

```sh
cd receiver
cargo run --release
```

Откройте **<http://127.0.0.1:8080>**. Сразу подключиться к известной плате можно так:

```sh
cargo run --release -- 192.168.1.61          # или 192.168.1.61:5005
```

В консоль раз в секунду печатается статистика: кадры, потери, повторы, перезапуски платы, а по каждому каналу RMS, смещение, гармоники 50 Гц и пики спектра.

### Веб-страница

- **Устройства.** Поиск запускается при открытии страницы, есть и кнопка «Найти». Для каждой платы показаны имя (`myocell-` и последние байты MAC), адрес, версия прошивки и состояние: свободна, занята (с адресом другого клиента), подключена, переподключение. Кнопки «Подключить» и «Отключить». При обрыве связи приёмник сам переподключается каждые 2 с, пока вы не нажмёте «Отключить».
- **Графики** включённых каналов за последние 5 с. Смещение вычитается только для отображения; пропуски данных показаны розовой полосой.
- **Статистика над графиком:** смещение, пик в процентах шкалы (жёлтый от 80 %, красный «НАСЫЩЕНИЕ» от 99 %), наводка 50 Гц, сигнал без сети. В шапке: кадров в секунду, потери, повторы, перезапуски.
- **«● Записать» / «■ Остановить».** Рядом показаны имя файла, длительность и число меток.
- **«⚑ Метка»**, клавиша **M** (в любой раскладке) или Enter в поле подписи. Метка ставится на последний принятый кадр и видна на графиках вертикальной линией.

### Файлы записи

Каталог `recordings/` в **текущем рабочем каталоге** приёмника.

**`ch34_ГГММДД_ЧЧММСС.csv`** (каналы, затем время начала):

```
index,time_s,CH3_uV,CH4_uV
3208448,0.0000,-10689.309,-430.369
3208449,0.0005,-10693.934,-420.475
```

- `index`: номер преобразования АЦП. Скачок означает потерянные кадры.
- `time_s`: время от начала записи **по номеру отсчёта** (`(index − первый) / 2000`), а не по часам компьютера.
- Значения в микровольтах с тремя знаками: шаг АЦП при усилении 12 равен 0,024 мкВ, так что точность не теряется.
- Объём около **280 МБ в час** для двух каналов.
- Если плата перезапустилась во время записи (нумерация начинается заново), запись продолжается **в новом файле**.

**`ch34_ГГММДД_ЧЧММСС_marks.csv`** создаётся при первой метке:

```
index,time_s,label
1178159,2.0195,метка 1
1180199,3.0395,"сжал, ""сильно"""
```

Шкала `time_s` та же, что в файле данных. Метка запаздывает на время доставки, обычно 50–150 мс.

Чтение в Python:

```python
import pandas as pd
data = pd.read_csv("recordings/ch34_261031_034605.csv")
marks = pd.read_csv("recordings/ch34_261031_034605_marks.csv")
```

### HTTP API

Им пользуется страница, но им можно управлять и из скриптов. Запросы без заголовка `Origin` (curl, Python) принимаются.

| Запрос | Тело | Ответ |
|---|---|---|
| `POST /api/discover` | — | JSON-список найденных плат (ответ примерно через 0,8 с) |
| `POST /api/connect` | `{"address": "192.168.1.61:5005"}` | 202 |
| `POST /api/disconnect` | — | 202 |
| `POST /api/record/start`, `/api/record/stop` | — | 202 |
| `POST /api/mark` | `{"label": "текст"}` (`Content-Type: application/json`) | 202 |
| `GET /ws` | — | WebSocket: `hello`, `samples`, `stats`, `recording`, `connection`, `mark` |

202 значит «принято». Результат приходит всем открытым вкладкам через WebSocket.

```sh
curl -X POST http://127.0.0.1:8080/api/record/start
curl -X POST -H 'Content-Type: application/json' -d '{"label":"сжал"}' http://127.0.0.1:8080/api/mark
```

### Безопасность

- Веб-интерфейс доступен **только с этого компьютера** (`127.0.0.1`).
- Запросы со **сторонних сайтов**, открытых в том же браузере, отклоняются по заголовку `Origin` (ответ 403). Это защищает и от чтения сигнала через WebSocket, и от запуска записи.
- Протокол платы **не шифруется и не требует пароля**: любой компьютер в той же сети может найти плату и подключиться, если она свободна.

## 8. Распространение приёмника на другие компьютеры и ОС

Приёмник — **один исполняемый файл**: веб-страница встроена в него при сборке, отдельных файлов, интерпретаторов и установщиков не нужно. Он работает на macOS, Linux и Windows. Все зависимости (tokio, axum, if-addrs, chrono) кроссплатформенные.

### 8.1. Сборка на целевом компьютере (самый простой путь)

1. Установите Rust: <https://rustup.rs>. Нужен stable **1.88 или новее**.
2. Скопируйте каталоги `receiver`, `protocol` и `ads1298` (приёмник ссылается на них по относительным путям) или весь репозиторий.
3. Соберите:

   ```sh
   cd receiver
   cargo build --release
   ```

4. Готовый файл: `receiver/target/release/receiver` (на Windows `receiver.exe`). Его можно скопировать куда угодно. Записи будут сохраняться в `recordings/` рядом с тем каталогом, **из которого** его запустили.

### 8.2. Готовые файлы для всех ОС через GitHub Actions

Собирать на каждой машине неудобно. Если репозиторий лежит на GitHub, CI соберёт файлы для всех ОС сразу. Пример `.github/workflows/receiver.yml` (в репозитории его пока нет):

```yaml
name: receiver
on: [push, workflow_dispatch]
jobs:
  build:
    strategy:
      matrix:
        include:
          - os: ubuntu-latest
            file: receiver
          - os: macos-latest      # Apple Silicon
            file: receiver
          - os: windows-latest
            file: receiver.exe
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - run: cargo build --release
        working-directory: receiver
      - uses: actions/upload-artifact@v4
        with:
          name: receiver-${{ matrix.os }}
          path: receiver/target/release/${{ matrix.file }}
```

Готовые файлы появятся на странице запуска CI в разделе Artifacts.

### 8.3. Кросс-компиляция с одного компьютера

Возможна, но требует линкера целевой ОС. Самый простой инструмент — `cargo-zigbuild`, использующий Zig как линкер:

```sh
cargo install cargo-zigbuild --locked      # плюс сам Zig: https://ziglang.org
rustup target add x86_64-unknown-linux-gnu x86_64-pc-windows-gnu
cargo zigbuild --release --target x86_64-unknown-linux-gnu
cargo zigbuild --release --target x86_64-pc-windows-gnu
```

Для повседневного использования надёжнее способы 8.1 или 8.2.

### 8.4. Особенности ОС

| ОС | Что учесть |
|---|---|
| **macOS** | Скачанный файл помечается «из интернета», и Gatekeeper не даст его запустить. Снять пометку: `xattr -d com.apple.quarantine receiver`. Для Intel-Mac нужна отдельная сборка (`x86_64-apple-darwin`) |
| **Windows** | При первом запуске брандмауэр спросит разрешение: разрешите доступ в **частных** сетях. Если сеть помечена как «общественная», ответы платы на поиск будут заблокированы |
| **Linux** | Строгий брандмауэр (ufw, firewalld) может отбрасывать ответы платы на поиск: они приходят с адреса платы, а запрос уходил на широковещательный адрес, и система не считает их «ответом». Разрешите UDP из локальной сети, например `sudo ufw allow from 192.168.1.0/24 proto udp` |
| **все** | Компьютер и плата должны быть в одной IP-подсети: широковещательный запрос не проходит через маршрутизаторы. Гостевые сети и режим изоляции клиентов на роутере не позволят найти плату |

## 9. Диагностика

| Симптом | Что проверить |
|---|---|
| Плата не находится | Лог платы: есть ли `Wi-Fi connected` и `IP address`? Компьютер в той же подсети? Брандмауэр (раздел 8.4)? Если адрес известен, подключитесь напрямую: `cargo run --release -- <IP>` |
| «занята (IP)» | К плате подключён другой приёмник. Отключите его или дождитесь обрыва (около 10 с после его закрытия) |
| Переподключение не проходит | Плата перезапускается, это нормально, подождите 10–20 с. Если долго не проходит, посмотрите лог платы: `espflash monitor --no-reset` |
| Во время записи были обрывы Wi-Fi | Данные не теряются, пока буфер платы не переполнен (~3 мин). В статистике растут «повторы», «потери» остаются 0 |
| Красное «НАСЫЩЕНИЕ», огромное смещение | Плохой контакт электродов. Смочите кожу, прижмите плату ровно, дождитесь, пока смещение перестанет меняться. См. также раздел 2 о резисторах смещения |
| Сильная наводка 50 Гц | Нет контакта с электродом RLD (J8) или плохой контакт сигнальных электродов |
| Лог платы пустой после прошивки | После сброса USB переподключается около 1–2 с, и ранние строки теряются. Это не ошибка |
| `missed` или `overtaken` больше 0 в логе платы | Задача захвата не успевает. Смотрите `edge->read done`: при значениях около 500 мкс запас исчерпан |

## 10. Разработка

```sh
# Компьютерные крейты: тесты и линтер
for c in ads1298 backlog protocol receiver; do (cd $c && cargo test && cargo clippy --all-targets); done

# Прошивка
cd firmware && . ~/export-esp.sh && cargo clippy --release
```

- В прошивке включён `clippy::large_stack_frames` с порогом 1 КиБ (`firmware/.clippy.toml`): стек задач маленький, и переполнение стека трудно отлаживать. Если форматирование одной большой строки лога превышает порог, вынесите её в отдельную функцию с `#[inline(never)]`.
- Предупреждение линкера `LOAD segment with RWX permissions` нормально для ESP32.
- Страница приёмника (`receiver/ui/index.html`) встраивается в бинарник через `include_str!`. После её правки приёмник нужно **пересобрать**, а в браузере обновить страницу (Cmd/Ctrl+Shift+R).
